# 第11章 テストとCI：品質を自動で守る

分量が多い章です。「テスト」（11-1〜11-5）と「CI」（11-6〜11-10）の2回に分けて進めてもかまいません。

## この章のゴール

テストを実行・読解・追加でき、CIでテストが自動実行され、失敗したPRがマージできない状態を体験します。

## 11-1 テスト用のNeonブランチと`.env.test`を用意する

### やること

開発用のデータベースとは別に、テスト専用のデータベースを用意します。テストのたびに中身を空にするため、開発用と同じものを使うと大切なデータが消えてしまいます。

### 操作

1. Neonのダッシュボードで、開発用プロジェクトの中に「test」という名前のブランチ（Neonの機能。Gitのブランチとは別の概念です）を作る
2. 「Connect」から、testブランチの接続文字列をコピーする
3. `.env.test.example`をコピーして`.env.test`を作る

```
copy .env.test.example .env.test
```

4. `DATABASE_URL=`の後ろにコピーした接続文字列を貼り付け、`APP_ENV=test`はそのままにする

### うまくいったときの結果

`.env`（開発用）と`.env.test`（テスト用）の2つのファイルができ、それぞれ違う接続文字列が入っている。

### うまくいかないとき

- `.env`と同じ接続文字列を貼ってしまうと、テスト実行時に安全装置が働いてエラーになります（11-2で確認します）

### テストファイルを用意する

## 11-6 CIを設定する

### やること

GitHub Actionsという仕組みを使い、pushやPRのたびに自動でテストが実行されるようにします。

### コード

`.github/workflows/ci.yml`というファイル（フォルダも新しく作る）を作り、次の内容を貼り付ける。

```yaml
name: CI

# mainやブランチにpushしたとき、プルリクエストを作ったときに実行する（第11章で説明）
on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest

    # テスト用に、このワークフローの中だけで使う一時的なPostgreSQLを起動する。
    # Neonではなく、GitHub Actionsが用意するコンテナを使う（第11章で説明）
    services:
      postgres:
        image: postgres:18
        env:
          POSTGRES_USER: postgres
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: tasks_test
        ports:
          - 5432:5432
        # PostgreSQLの起動が終わるのを待ってから、次のステップに進むための確認
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    env:
      # 上のPostgreSQLへの接続文字列。SSLは使わない（第9章のNeonとの違い）
      DATABASE_URL: postgresql://postgres:postgres@localhost:5432/tasks_test
      APP_ENV: test

    steps:
      - name: リポジトリを取得する
        uses: actions/checkout@v4

      - name: Node.jsをセットアップする
        uses: actions/setup-node@v4
        with:
          node-version: '24'

      - name: 依存関係をインストールする（package-lock.jsonのバージョンどおりに）
        run: npm ci

      - name: テストを実行する
        run: |
          # テストが1件も実行されないまま、CIが成功扱いにならないようにする。
          # node --testは0件でも終了コード0になるため、実行結果の件数を
          # 自分で確認している（第11章で説明。完成済みのコードとして提供）
          set -o pipefail
          npm test | tee test-output.txt
          test_exit_code=$?
          if grep -q "tests 0" test-output.txt; then
            echo "テストが1件も実行されていません。tests/にテストファイルがあるか確認してください。"
            exit 1
          fi
          exit $test_exit_code
```

これは完成済みのコードとして提供します（YAMLの書き方自体は深入りしません）。この講座のNeonの代わりに、GitHub Actionsが用意する一時的なPostgreSQL（SSLなし）を使っている点に注目してください。

### 操作

```
git add .
git commit -m "CIを設定する"
git push
```

GitHubのリポジトリページで「Actions」タブを開く。

### うまくいったときの結果

Actionsタブに実行結果が表示され、緑のチェックマークが付く。

［スクショ ch11-1：GitHub Actionsの実行結果（緑）］

### うまくいかないとき

- YAMLはインデント（字下げ）がずれるとエラーになります。貼り付けた内容がそのままになっているか確認してください

## 11-7 `main`に「CIが成功しないとマージできない」ルールを設定する

### やること

GitHubの「Rulesets」という機能で、テストが通らないPRをマージできないようにします。

### 操作

1. （事前準備）11-6で一度CIを実行しているので、そのまま進めます（チェック名は一度も実行されていないと選択肢に出てこないため）
2. リポジトリの「Settings」タブを開く
3. 左メニュー「Code and automation」の中の「Rules」→「Rulesets」を開く
4. 「New ruleset」→「New branch ruleset」を選ぶ
5. 「Ruleset Name」に名前を付け（例：`main保護`）、「Enforcement status」を「Active」にする
6. 「Target branches」の「Add target」→「Include default branch」を選ぶ
7. 「Branch rules」の「Require status checks to pass」にチェックを入れ、「Add checks」で`test`（`ci.yml`の`jobs.test`の名前）を検索して追加する
8. 「Create」で保存する

### うまくいったときの結果

設定が保存される。

［スクショ ch11-3〜7：Rulesets設定画面の各ステップ］

### うまくいかないとき

- 「Add checks」で`test`が候補に出てこない場合、11-6でCIを一度も実行できていない可能性があります。11-6に戻って確認してください

<details>
<summary>ヒント3：コードの例</summary>

`src/db.js`：

```js
async function updateTask(id, updates) {
  const currentResult = await pool.query('SELECT * FROM tasks WHERE id = $1', [id]);
  if (currentResult.rows.length === 0) {
    return null;
  }
  const currentTask = currentResult.rows[0];

  let newTitle = currentTask.title;
  if (typeof updates.title === 'string') {
    newTitle = updates.title;
  }
  let newDone = currentTask.done;
  if (typeof updates.done === 'boolean') {
    newDone = updates.done;
  }

  const result = await pool.query(
    'UPDATE tasks SET title = $1, done = $2 WHERE id = $3 RETURNING *',
    [newTitle, newDone, id]
  );
  return mapRowToTask(result.rows[0]);
}
```

`src/app.js`：

```js
async function updateTask(req, res) {
  try {
    if (!req.body) {
      res.status(400).json({ error: 'JSON形式で、Content-Type: application/json を付けて送ってください' });
      return;
    }

    const doneIsSent = typeof req.body.done === 'boolean';
    const titleIsSent = typeof req.body.title === 'string';
    if (doneIsSent === false && titleIsSent === false) {
      res.status(400).json({ error: '完了状態（done）かタイトル（title）のどちらかを送ってください' });
      return;
    }

    const updates = {};
    if (doneIsSent) {
      updates.done = req.body.done;
    }
    if (titleIsSent) {
      const title = req.body.title.trim();
      if (title === '' || title.length > 100) {
        res.status(400).json({ error: 'タイトルは1文字以上100文字以内で入力してください' });
        return;
      }
      updates.title = title;
    }

    const taskId = Number(req.params.id);
    const updatedTask = await db.updateTask(taskId, updates);
    if (updatedTask === null) {
      res.status(404).json({ error: 'タスクが見つかりません' });
      return;
    }
    res.json(updatedTask);
  } catch (error) {
    respondToError(res, error);
  }
}
```
