# 第12章 デプロイ：本番環境に公開する

## この章のゴール

自分のアプリをRenderとNeonで公開し、`main`へのマージで自動的に本番に反映されることを確認できるようになります。

**この章の画面は、講師がフェーズ3で実際に操作したときのスクリーンショットを使っています。**画面の項目名やボタンの位置は変わることがあるので、実際の画面と違う場合は講師・TAに確認してください。

## 12-1 Neonで「本番用」プロジェクトを作る

### やること

これまでの開発用・テスト用とは別に、本番用のプロジェクトを作ります。

### 操作

1. https://console.neon.tech を開き、「New Project」をクリックする
2. Project Name：例）`kantan-task-prod`
3. Postgres version：開発用と同じ（18）
4. Region：**第9章で開発用プロジェクトを作ったときと同じリージョン**を選ぶ
5. 「Create Project」をクリックする

### うまくいったときの結果

新しいプロジェクトのダッシュボードが表示される。

［スクショ ch12-1：Neon本番プロジェクト作成画面］

---

## 12-2 RenderでWebサービスを作る

### やること

Renderのアカウントを作り（事前課題で作成済みのはずです）、自分のリポジトリと連携してWebサービスを作ります。

### 操作

1. https://render.com を開き、「New +」→「Web Service」
2. 自分のGitHubアカウントと連携し、リポジトリの一覧から自分のリポジトリを選ぶ
3. 次を設定する
   - Name：例）`kantan-task`
   - Region：Neonの本番プロジェクトと近いリージョン
   - Branch：`main`
   - Language：Node
   - Build Command：`npm ci`
   - Start Command：`npm start`
   - Instance Type：**Free**

### うまくいったときの結果

設定画面に入力が反映される（この時点ではまだ作成しない。12-3の環境変数もあわせて設定してから作成してよい）。

［スクショ ch12-2：Render Web Service作成フォーム］

---

## 12-3 環境変数`DATABASE_URL`とヘルスチェックを設定する

### やること

Neonの本番用接続文字列をRenderに設定し、正常性確認のパスも設定します。

### 操作

1. 「Environment」タブ（作成前なら同じ画面内）で「+ Add Environment Variable」
2. Key：`DATABASE_URL`、Value：12-1で確認したNeonの接続文字列
3. 末尾が`?sslmode=require`の場合は、`?sslmode=verify-full`に書き換える（第9章と同じ対応）
4. 「Settings」の「Health Checks」で、Health Check Pathに`/health`を入力する
5. 「Create Web Service」をクリックする

### うまくいったときの結果

初回デプロイが始まる。

［スクショ ch12-3：Render「Environment」タブの`DATABASE_URL`設定画面（値は伏せてあります）］
［スクショ ch12-4：ヘルスチェックパス設定画面］

### うまくいかないとき

- 接続文字列を貼り間違えると、次のログで気づけます（12-4参照）

### やること

## 12-5 公開URLを開く

### やること

自分のアプリが、インターネット上に公開されたことを確認します。

### 操作

画面右上に表示される公開URL（`https://(サービス名).onrender.com`）を開く。スマートフォンからも同じURLを開いてみる。

### うまくいったときの結果

`/`でアプリの画面が、`/health`で`{"status":"ok"}`が表示される。第0章と同じように、タスクの追加・完了・削除ができる。

［スクショ ch12-6：公開URLでのアプリ表示］

### 考えてみよう

無料プランは15分間アクセスがないと止まり、次のアクセスで起動に1分ほどかかることがあります（第0章で体験したとおりです）。

## 12-6 画面の文言を変えて、一周確認する

### やること

ブランチ→PR→CI→マージ→自動デプロイの一連の流れを、実際に一周体験します。**すでに第11章で`main`にブランチ保護（CIが成功しないとマージできないルール）を設定済み**なので、この章では「保護された状態で、正しく開発を進めるとどうなるか」を体験することになります。

### コマンド・操作

1. ブランチを作る：`git switch -c change-heading-text`
2. `public/index.html`の見出し（`<h1>かんたんタスク</h1>`）を好きな文言に変える
3. コミット・push：`git add .`→`git commit -m "見出しの文言を変える"`→`git push -u origin change-heading-text`
4. PRを作る
5. CIが緑になるのを待つ
6. マージする
7. Renderの「Logs」タブで、自動的に新しいデプロイが始まることを確認する
8. 公開URLを開き、文言が変わっていることを確認する

### うまくいったときの結果

コードをマージしただけで、何も手動操作をしていないのに、公開URLの表示が変わる。

### 考えてみよう

なぜ「`main`にマージしただけ」で本番に反映されたのでしょうか。Renderの設定（Branch：`main`）と関係があります。

## 12-7 リポジトリに秘密情報が含まれていないことを確認する

### やること

自分のGitHubリポジトリを確認し、接続文字列などが誤って公開されていないかチェックします。

### 操作

GitHub上で自分のリポジトリを開き、`.env`というファイルが**存在しない**こと（`.gitignore`で管理対象外になっているため）、コミット履歴にも接続文字列が出てこないことを確認する。

### うまくいったときの結果

`.env`がリポジトリに含まれていない。含まれている場合は、すぐに講師に相談してください（接続文字列を無効化して作り直す必要があります）。

---

## この章の確認チェック

- 公開URLでアプリが動く
- ブランチ保護がある状態で、PR→CI→マージだけで本番に反映されることを確認した
- `.env`がリポジトリに含まれていない
